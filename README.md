# Определение цвета предмета на фото и с веб-камеры

Первая версия для мини-склада: Python + OpenCV, без обучения нейросети.
Программа выделяет один светлый или цветной предмет на чёрном конвейере
и определяет его цвет, исключая фон.

## Установка и запуск

Нужен Python 3.10 или новее. В терминале из каталога проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python color_detector.py
```

В Windows активация окружения: `.venv\Scripts\activate` (cmd) или
`.venv\Scripts\Activate.ps1` (PowerShell); вместо `python3` обычно используется `python`.

Положите фотографии в папку `photos/` рядом с программой и запускайте без аргументов:

```bash
.venv/bin/python color_detector.py
```

Программа обработает все JPG, JPEG, PNG, BMP, WEBP и TIFF в этой папке
(без вложенных папок). Файлы остаются на месте; при каждом запуске обрабатываются
все фотографии заново. Если папка пустая, программа попросит добавить фотографии.
Ошибка в одном файле не мешает обработке остальных; при наличии ошибок код выхода — 1.
Папки `photos/` и `output/` по умолчанию определяются относительно файла программы,
поэтому запуск из другого рабочего каталога тоже работает.

При необходимости можно по-прежнему указать отдельную фотографию или другую папку:

```bash
python color_detector.py "/путь/к/фотографии.jpeg"
python color_detector.py "/путь/к/папке"
```

Проверено на фотографии Apple Pencil на чёрном коврике: **белый**, доля основного
цвета **90,2%**, медианный RGB **[225, 224, 212]**. Контур проверен визуально:
коврик и светлый стол по краям снимка не входят в выделенный предмет.

В терминале появятся название цвета, доля пикселей этого цвета и медианный RGB.
Каждый запуск создаёт в `output/` отдельную папку с датой и временем
начала обработки: `ph_ММ.ДД ЧЧ.ММ` (без года и секунд).
Время всегда в **UTC+3**, независимо от часового пояса компьютера. В ней сохраняются:

- `ИМЯ_result.jpg` — фотография с контуром предмета и названием цвета;
- `ИМЯ_mask.png` — маска: белым выделен предмет, чёрным фон;
- `ИМЯ_result.json` — цвет, распределение цветов и имя исходной фотографии (`source_file`).

Например:

```text
output/
  ph_09.18 10.35/
    ph_09.18 10.35_result.jpg
    ph_09.18 10.35_mask.png
    ph_09.18 10.35_result.json
  ph_09.18 10.37/
    ph_09.18 10.37_result.jpg
    ph_09.18 10.37_mask.png
    ph_09.18 10.37_result.json
```

Путь к папке текущего запуска выводится в терминале. Если имя папки уже занято
(например, при нескольких запусках за минуту), добавляется номер: `_02`, `_03` и т. д.
Прошлые результаты сохраняются. Для пустой входной папки папка запуска не создаётся.
Основной каталог можно изменить через `--output-dir results` — папки запусков
будут создаваться внутри него.
Если фотографий несколько, к имени каждого комплекта добавляется номер фотографии:
`ph_09.18 10.35_01_mask.png`, `ph_09.18 10.35_02_mask.png` и т. д.
Фотографии нумеруются в порядке сортировки по имени. Соответствие исходнику
видно в терминале и в поле `source_file` JSON-файла.

## Как выбирается предмет

Алгоритм рассчитан на **чёрный фон**. Чёрная лента при освещении может выглядеть
серой, поэтому порог яркости подбирается по снимку методом Оцу, но не опускается
ниже 95 по шкале 0…255. Светлые пиксели выше порога считаются кандидатами на предмет.
Насыщенные цветные пиксели выделяются дополнительно: насыщенность от 65,
яркость от 65, разница максимального и минимального канала от 40.
Это помогает находить, например, тёмно-синий предмет на тёмной ленте.

Медианный фильтр подавляет мелкую фактуру фона. Из связных областей выбирается
самая крупная, не касающаяся границы кадра или ROI. Так светлый стол за краями
коврика не попадает в результат. Мелкий шум отбрасывается по площади. Маска
дополнительно проверяется по исходным пикселям, чтобы сглаживание не добавляло
тёмный фон. Изображение не уменьшается перед выделением тонких предметов.

Предмет должен целиком находиться внутри кадра/ROI с небольшим запасом до границ.
Алгоритм выделяет предмет по внешнему виду и не определяет, что это именно Pencil.
Цвет вычисляется только внутри маски; прямоугольная область вокруг предмета
не используется для подсчёта цвета.

Если объектов несколько или фон сложный, укажите прямоугольник вокруг нужного
предмета с небольшим запасом фона: `--roi X Y WIDTH HEIGHT`.
Координаты задаются в пикселях исходного снимка после применения EXIF-ориентации;
начало координат — левый верхний угол.
Весь предмет должен попасть внутрь прямоугольника.

```bash
python color_detector.py photo.jpg --roi 100 600 1700 950
```

Это пример координат для крупного снимка; для своего изображения их нужно подобрать.

## Как определяется цвет

После выделения объекта программа немного отступает от его контура и переводит
пиксели в HSV. Цветовой тон определяет красный, оранжевый, жёлтый, зелёный,
голубой, синий, фиолетовый, розовый и коричневый. Яркость и насыщенность позволяют
отдельно выделять чёрный, серый и белый. Побеждает наиболее частый класс.
Пороговые значения находятся в функции `classifyPixels` в `color_detector.py`.

`dominant_share` — доля пикселей основного цвета, **не вероятность правильного
распознавания**. При доле ниже 60% результат отмечается как `ambiguous`:
предмет может быть разноцветным или маска неточной. RGB — медиана пикселей
победившего класса в порядке красный, зелёный, синий.

Это прототип для одного хорошо различимого предмета на чёрном фоне.
Чёрные предметы и почти чёрные участки исключаются вместе с фоном; первый пример
с чёрной мышкой на светлом столе больше не соответствует рабочему режиму.
Сильные блики на ленте, цветное освещение, малый контраст, прозрачные предметы
и яркий мусор могут приводить к ошибкам. Пороги нужно проверить на реальных
образцах при освещении склада. Если предмет касается края, он исключается;
дождитесь его полного появления в рабочей области.
Сначала проверяйте маску — она показывает, какой участок анализируется.

## Веб-камера: живое изображение с обводкой

Запуск из каталога проекта:

```bash
.venv/bin/python camera_detector.py
```

Откроется отдельное окно **Warehouse - live color** с непрерывным изображением
веб-камеры, зелёным контуром предмета, названием цвета и долей пикселей этого цвета.
Внизу отображается скорость обработки FPS. Названия цветов в окне — на английском,
как и на сохранённых фотографиях. При отсутствии предмета появляется `No object`;
прежний контур и цвет сразу убираются. Выбирается один самый крупный предмет.

В окне камеры доступны клавиши (английская раскладка):

- **Esc / Q** — остановить камеру и закрыть окно;
- **S** — сохранить результат текущего кадра, маску и JSON в `output/ph_ММ.ДД ЧЧ.ММ/`.

Окно также можно закрыть обычной кнопкой закрытия. Запись всего видео не ведётся:
файлы создаются только по S, если предмет найден. Снимки одной сессии имеют номера
`_01`, `_02` и т. д.; время папки соответствует первому сохранению. В JSON есть
`source_file` с индексом камеры и `captured_at` со временем снимка в UTC+3.

По умолчанию используется камера **0**. Если открылась встроенная камера вместо
подключённой веб-камеры, попробуйте:

```bash
.venv/bin/python camera_detector.py --camera 1
```

Индекс может быть 0, 1, 2 и т. д. Для меньшей нагрузки можно запросить 640×480:

```bash
.venv/bin/python camera_detector.py --camera 0 --width 640 --height 480
```

По умолчанию запрашивается 960×540 и 30 кадров/с. Камера может выбрать другой
поддерживаемый режим; фактический размер выводится в терминале. FPS в окне —
измеренная скорость цикла получения, обработки и показа, а не обещанная частота камеры.
По умолчанию распознавание ограничено красным прямоугольником по отметке на
скриншоте от 30.09.2026: левый верхний угол — 23% ширины и 16% высоты кадра,
размер — 52% ширины и 64% высоты. Рамка, нарисованная от руки, приближена
обычным прямоугольником. При кадре 960×540 это `221 86 499 346`.
Область автоматически масштабируется под фактическое разрешение камеры;
изменение размера окна на неё не влияет. В живом просмотре она обведена красным,
а её координаты выводятся в терминале. Предметы снаружи не распознаются.

Эта настройка общая для `Camera()`, `camera_detector.py` и `main.py`.
Чтобы заменить её, передайте `--roi X Y WIDTH HEIGHT` в пикселях
**фактического кадра**, до изменения размера окна:

```bash
.venv/bin/python camera_detector.py --roi 100 50 600 400
.venv/bin/python main.py --port COM3 --weight-scale=123.45 --roi 100 50 600 400
```

`X Y` — левый верхний угол, `WIDTH HEIGHT` — ширина и высота области.
Флаг действует для текущего запуска; без него используется область по умолчанию.
Для анализа всего кадра укажите `--roi 0 0 WIDTH HEIGHT` с фактическими размерами.

### Фильтрация шума камеры

В `Camera()` и живом просмотре предмет по умолчанию должен занимать хотя бы
**0,2% площади ROI** (и не менее 25 пикселей), иметь ширину и высоту
**от 8 пикселей** и наблюдаться **3 последовательных кадра**.
Площадь считается по выделенным пикселям, ширина и высота — по охватывающему
прямоугольнику. При ROI 499×346 минимальная площадь получается 346 пикселей.
Размер проверяется до выбора самого крупного кандидата.

При подтверждении сравниваются соседние кадры: цвет должен совпадать,
отношение меньшей ширины к большей и меньшей высоты к большей — быть не ниже
0,6, а площадь пересечения прямоугольников, делённая на площадь их объединения
(IoU), — не ниже 0,25. Это допускает небольшое движение предмета.
Потеря предмета или смена кандидата сбрасывает подтверждение; смена ROI,
разрешения, настроек и переподключение камеры также начинают его заново.
В окне до подтверждения отображается `Confirming object: 1/3`, без контура
и цвета. Сохранять снимок можно после подтверждения. Исчезнувший предмет
немедленно убирается с изображения и из результата API.

Пример более строгих настроек для живого просмотра:

```bash
.venv/bin/python camera_detector.py --min-area-fraction 0.005 --min-width 12 --min-height 12 --confirmation-frames 5
```

`0.005` означает 0,5% площади ROI. Эти же параметры доступны в конструкторе
`Camera(min_area_fraction=0.005, min_width=12, min_height=12, confirmation_frames=5)`;
`main.py` использует значения конструктора по умолчанию.
`confirmation_frames=1` отключает ожидание подтверждения, сохраняя фильтр размера.
Пороги подбираются по самому маленькому предмету и записи пустой ленты.
Слишком большие пороги отсекают полезные предметы, а быстрое движение или
нестабильный цвет могут мешать подтверждению. Постоянное крупное пятно или тень
могут пройти эти фильтры. Проверка прибытия в точку разгрузки остаётся отдельной задачей.

На Mac при первом запуске разрешите доступ к камере приложению, из которого
запускается Python (например, Terminal или IDE). Если доступ запрещён, проверьте
«Системные настройки → Конфиденциальность и безопасность → Камера» и перезапустите
программу. Другие приложения могут занимать камеру — закройте их при ошибке открытия.

Для окна нужна обычная сборка `opencv-python`. При обновлении старой установки,
где использовалась `opencv-python-headless`, выполните:

```bash
.venv/bin/python -m pip uninstall -y opencv-python-headless
.venv/bin/python -m pip install --upgrade -r requirements.txt
```

Не устанавливайте обе сборки одновременно: они используют один модуль `cv2`.
Описание захвата видео — в [документации OpenCV](https://docs.opencv.org/4.x/dd/d43/tutorial_py_video_display.html),
выбор сборки — в [инструкции opencv-python](https://github.com/opencv/opencv-python#installation-and-usage).

## Общая обработка фото и видео

`detectColor(image, roi=None, background="white")` принимает BGR-кадр NumPy и возвращает словарь
результата и маску. Фото и веб-камера используют одну функцию определения цвета
и одну функцию `drawResult` для отрисовки. Отсутствие предмета обозначается
исключением `ObjectNotFound`: в видео оно означает пустой кадр, а не остановку программы.
Параметры `min_area_fraction`, `min_width`, `min_height` можно передавать по имени
в `detectColor` и `segmentObject`. Для фото сохранены мягкие пороги
`0.00005`, `1`, `1`; фильтрация по нескольким кадрам применяется только в `Camera`.
Для конвейера следующим шагом стоит зафиксировать область анализа и освещение,
снять пустую ленту и образцы всех нужных цветов. Это позволит настроить выделение
предметов и цветовые пороги. При быстром движении качество зависит от освещения,
выдержки и размытия кадра; предмет должен полностью войти в кадр/ROI.

## API камеры

`camera.py` содержит класс `Camera` для будущего управляющего скрипта.
Подключение и обработка кадров вынесены из `camera_detector.py`; живое окно
использует тот же класс, а алгоритм цвета остаётся общим с обработкой фотографий.

```python
from camera import Camera

camera = Camera(camera_index=0, roi=(100, 60, 300, 300))
try:
    result = camera.detectObject()
    if result is not None:
        print(result["color"], result["rgb"], result["bbox"])
finally:
    camera.disconnect()
```

ROI — область распознавания `(x, y, width, height)` в пикселях фактического кадра;
подберите её под место считывания на конвейере. Без явной ROI используется
общая область по умолчанию из `camera.py`, описанная выше.
Предмет должен целиком находиться внутри области, не касаясь её края.

- `init()` — подключение, автоматически вызывается конструктором. После
  `disconnect()` можно подключиться повторно.
- `getFrame()` — следующий BGR-кадр камеры.
- `detectObject(frame=None)` — распознать предмет на переданном или новом кадре.
  Возвращает словарь с `color`, `color_ru`, `rgb`, `bbox`, `dominant_share`,
  `ambiguous`, `color_shares`; если предмет не найден — `None`.
- `processFrame(frame=None)` — получить кадр с обводкой, тот же словарь и маску.
- `isObjectReady(result)` — плейсхолдер с `NotImplementedError` для проверки,
  что объект подъехал в нужное положение. Допуск и подтверждение по нескольким
  кадрам ещё предстоит определить.
- `disconnect()` — освободить камеру.

API не открывает окно и не сохраняет файлы. При ошибке получения кадра выдаётся
`RuntimeError`, при неверной ROI — `ValueError`. Отсутствие предмета не подменяется
результатом предыдущего кадра. До подтверждения `detectObject()` возвращает `None`,
а `processFrame()` — кадр без обводки, `None`, `None`.
Передавая кадры вручную, обрабатывайте каждый новый снимок один раз:
повторная передача того же снимка тоже увеличивает счётчик.
Повторные вызовы после подтверждения продолжают возвращать текущий предмет:
однократная обработка каждого объекта пока не реализована.
`dominant_share` показывает долю основного цвета, а не вероятность правильного
ответа. Как и исходный детектор, класс рассчитан на светлые или цветные предметы
на чёрной ленте.

## API оборудования

`hardware.py` содержит класс `Hardware` для связи с Arduino/ESP32 по serial.
Зависимость `pyserial` включена в `requirements.txt`.

```python
from hardware import Hardware

hardware = Hardware(com_port="COM3", baudrate=115200)
try:
    hardware.zero()
    responses = hardware.goto(10, 20)
    hardware.waitForMovement()
    print(responses)
finally:
    hardware.disconnect()
```

API соответствует `sketch_sep22a.ino`: 115200 бод, команды ASCII с завершающим
переводом строки. Конструктор вызывает `init()` и ждёт стартового `READY`
до `startup_timeout` секунд (по умолчанию 10). `READY` отправляется после
стартового тарирования HX711; тара должна быть пустой. Если плата не перезапускается
при открытии порта и не отправляет `READY`, подключение завершится таймаутом.
Повторный `init()` при исправном открытом соединении ничего не делает;
после ошибки протокола он выполняет синхронизацию через `STOP`,
после `disconnect()` подключается заново.

| Метод | Команда | Ожидаемый ответ |
| --- | --- | --- |
| `goto(x, y)` | `GOTO x y` | `OK`, позднее `DONE` |
| `move(dx, dy)` | `MOVE X dx`, `MOVE Y dy` для ненулевых смещений | `OK` для каждой команды, `DONE` при достижении обеих целей |
| `jog(axis, direction)` | `X+`, `X-`, `Y+`, `Y-` | `OK`, `DONE` при достижении цели |
| `getPosition()` | `POS?` | `POS x y` |
| `stop()` | `STOP` | `STOPPED` |
| `zero()` | `STOP`, затем `ZERO` | `STOPPED`, затем `ZEROED` |
| `setServo(angle)` | `SERVO angle` | `SERVO angle` |
| `get_weight()` | `WEIGHT?` | `WEIGHT grams`, метод возвращает `float` в граммах |
| `get_weight(fast=True)` | `WEIGHT_FAST?` | `WEIGHT grams`, среднее 2 новых отсчётов без выдержки |
| `tareWeight()` | `TARE` | `TARED` |
| `calibrateWeight(grams)` | `CALIBRATE grams` | `SCALE factor`, метод возвращает коэффициент |
| `setWeightScale(factor)` | `SCALE factor` | `SCALE factor`, метод возвращает коэффициент |

Координаты и смещения — в миллиметрах; коэффициенты шагов на миллиметр в прошивке
пока требуют калибровки. `POS` возвращает программные координаты с двумя знаками
после запятой. `MOVE` отсчитывает смещение от текущей позиции на момент обработки
каждой команды, а не от предыдущей цели. `jog()` принимает ось `X`/`Y` и направление
`1`/`-1`: прошивка задаёт цель на 1000000 шагов, так что движение не бесконечное.
Остановить его можно через `stop()`. `STOP` останавливает XY и отменяет
текущее измерение HX711, но не выключает конвейер и не останавливает серво.

Методы из таблицы возвращают список строк, прочитанных до ожидаемого ответа,
и ждут его до `timeout` секунд (по умолчанию 1). `ERROR`, `UNKNOWN`, неожиданные
ответы и перезапуск платы вызывают исключения. После ошибки/таймаута перед новыми
командами нужно вызвать `stop()` для синхронизации или переподключиться.
Сброс координат после перезапуска требует восстановления калибровки механики.

`waitForMovement()` ожидает `DONE` в пределах `movement_timeout` (по умолчанию
60 секунд). Ответ `DONE` не теряется, если ранее был прочитан через `getPosition()`,
другую команду или `readResponse()`. Строки, поступившие частями, собираются целиком.
`DONE` означает окончание выдачи шагов, но не подтверждает позицию датчиками.
Низкоуровневый `send()` только записывает команду; для обычной работы используйте
методы из таблицы. Вызовы API должны выполняться последовательно, из одного потока.

`open()` и `close()` устанавливают углы сервопривода 127° и 37° соответственно.
`setServo()` принимает только целый угол 0–180°; ошибочные значения API отклоняет
до отправки, хотя сама прошивка ограничивает их диапазоном. Ответ `SERVO angle`
подтверждает вызов `my_servo.write()`, а не завершение движения.
`waitUntilIdle()` ждёт XY, затем выдержку после последней команды серво.
Для неё нужно задать `servo_settle_time` в секундах при создании `Hardware`
(в главном скрипте — в `createHardware()`). Значение необходимо подобрать
на механике; по умолчанию оно 0,5 секунды. При явном `None` ожидание после команды
серво вызывает `NotImplementedError`. Выдержка не заменяет обратную связь от датчика.

`conveyor_on()` / `conveyor_off()` отправляют `CONVEYOR ON` / `CONVEYOR OFF`
и ждут одноимённого ответа. Скорость задаётся в прошивке.
`feedOneObject(duration=0.3)` включает конвейер, после подтверждения включения
ждёт `duration` секунд и выключает его. При исключении или `Ctrl+C` также
выполняется попытка выключения. Длительность должна быть конечной и положительной.
`waitForUnload()` выдерживает 0,5 секунды перед закрытием затвора.
Обе выдержки требуют проверки на механике: датчика фактического падения нет.
`get_weight()` получает реальный вес HX711; ниже описана необходимая калибровка.
Для освобождения порта используется отдельный `disconnect()`, который отправляет
`STOP`, ждёт `STOPPED` и закрывает соединение даже при ошибке ожидания.

Консоль запускается командой `python controller.py` и использует тот же класс.
Команды `conveyor on` и `conveyor off` отдельно включают и выключают конвейер.
При выходе из консоли, включая `Ctrl+C` и ошибки, выполняются отдельные попытки
остановить головку, выключить конвейер и закрыть соединение.
При импорте модулей соединение не открывается и консоль не запускается.

### Запуск сортировки из контроллера

Контроллер может запускать цикл `main.py` в фоне на уже открытом соединении:

```bash
.venv/bin/python controller.py --port /dev/cu.usbserial-3120 --weight-scale=123.45
```

Замените порт и коэффициент своими значениями. Вместо `--weight-scale` можно
выполнить `scale K` или `calibrate G` в консоли до запуска сортировки.
Контроллер принимает те же параметры камеры, ROI, времени подачи и взвешивания,
границ и минимальной массы, что и `main.py`.

```text
main start
weight continuous
```

`main` без аргументов тоже запускает сортировку. Она использует текущую
калибровку и тарирует пустую платформу перед запуском и после выгрузки каждого объекта.
Команда `main status` показывает состояние и последнюю ошибку.

Фоновые сообщения камеры и сортировщика записываются с отметкой времени в
`output/sorter.log`. При первом `main start` на macOS автоматически открывается
отдельное окно Terminal с обновляемым журналом. В исходном терминале остаются
ввод команд и ответы на них. Сообщения из отдельных запусков добавляются в
конец файла; окно показывает последние 100 строк и новые записи.

Команда `main log` открывает окно журнала повторно, например после его закрытия.
Закрытие окна журнала или `Ctrl+C` в нём завершает только просмотр — сортировка
продолжается. Для остановки используйте `main stop` в контроллере.
Если macOS не разрешила открыть окно, контроллер напечатает готовую команду
`tail` для запуска в другом терминале; сообщения продолжат записываться в файл.
Параметр `--sorter-log PATH` меняет путь журнала, а `--no-log-window` отключает
автоматическое открытие окна. `main log` работает и с этим параметром.
При отдельном запуске `main.py` сообщения по-прежнему выводятся в его терминал.

Во время сортировки доступны `weight`, `weight continuous`, `main status`, `main log`,
`help`, `main stop`, `stop` и `quit`/`exit`. Команды движения, конвейера,
тарирования, калибровки и `pos` блокируются: оборудованием управляет только
поток сортировки. Повторный `main start` не создаёт второй поток.

`weight` показывает последнее показание сортировщика и его возраст.
`weight continuous` показывает новые показания, полученные во время штатного
взвешивания, включая отрицательные. Между взвешиваниями вывод ждёт новых данных;
явно запрошенный просмотр веса остаётся в терминале контроллера до `Ctrl+C`.
Дополнительных запросов веса нет. Это необходимо, поскольку во время измерения
прошивка отклоняет другие команды как `HX711_BUSY`, а при движении XY
запрещает взвешивание. Вне сортировки обе команды опрашивают весы как раньше.

`Ctrl+C` во время просмотра веса завершает только просмотр. `main stop` или
`stop` останавливает сортировку и механизмы, освобождает камеру и оставляет
соединение открытым для ручного управления и повторного запуска. Ожидание
ответа платы и паузы подачи/выгрузки прерываются по запросу остановки.
`quit`, конец ввода или `Ctrl+C` в приглашении команд сначала останавливает
фоновый цикл, затем отключает оборудование. При ошибке фонового цикла
механизмы останавливаются, а консоль остаётся доступной.

## HX711: подключение и калибровка

Подключение к Arduino: **DT/DOUT → A5, SCK/CLK → A4**, общий GND.
Тензодатчик подключается к входу A модуля HX711. Скетч читает канал A
с усилением 128 без дополнительной библиотеки HX711; библиотека Servo нужна,
как и раньше. Формат отсчётов и тактирование соответствуют
[документации HX711](https://cdn.sparkfun.com/datasheets/Sensors/ForceFlex/hx711_english.pdf).

При старте плата выключает конвейер, закрывает затвор, сбрасывает HX711,
выдерживает 0,5 секунды и усредняет 10 новых отсчётов пустой тары.
Только после успешного тарирования приходит `READY`. Первое накопленное
показание отбрасывается; во время выдержки данные также считываются и отбрасываются.
Каждое последующее измерение использует такую же выдержку и усреднение.
Это усреднение, а не проверка стабильности: при вибрации нужно проверить
механику и подобрать `SCALE_SETTLE_MS` в скетче.

Тарирование определяет ноль; для перевода в граммы отдельно нужен коэффициент:
`масса = (среднее АЦП − тара) / коэффициент`.
Первичная калибровка:

1. Прошить `sketch_sep22a/sketch_sep22a.ino`. Убрать предметы из тары.
2. Запустить `.venv/bin/python controller.py --port /dev/cu.usbserial-…`.
   При открытии порта Arduino обычно перезапускается и автоматически тарируется.
3. При необходимости повторить `tare` на пустой неподвижной таре.
4. Положить груз известной массы, например **10 г**, и в консоли выполнить
   `calibrate 10`. Команда вернёт коэффициент и готовый параметр
   `--weight-scale=...`. Знак коэффициента может быть отрицательным.
5. Командой `weight` проверить массу эталона, затем других известных грузов.
   Сохранить полученный коэффициент. В следующем сеансе консоли его можно
   установить через `scale <коэффициент>`.
6. Убрать груз, выйти командой `quit` и запускать сортировку с сохранённым
   коэффициентом. При новом подключении тара снова должна быть пустой.

Коэффициент хранится в RAM до перезапуска, в EEPROM не записывается.
Команда контроллера `weight continuous` непрерывно запрашивает и выводит массу
в граммах. `Ctrl+C` отменяет текущее измерение и возвращает к приглашению команд,
сохраняя подключение. Частота обновления определяется выдержкой и усреднением
в прошивке; обычная команда `weight` выводит одно измерение.

Для быстрого просмотра вне сортировки используйте `weight fast continuous`
(также допустимо `weight continuous fast`), для одного быстрого измерения —
`weight fast`. Сначала загрузите обновлённый `sketch_sep22a/sketch_sep22a.ino`
на Arduino: драйвер отправляет новую команду `WEIGHT_FAST?`.
Этот режим отбрасывает первый, потенциально старый отсчёт, затем усредняет
2 новых отсчёта без выдержки 500 мс. При HX711 в режиме 10 отсчётов/с
ожидается примерно 3–5 обновлений/с; реальная частота зависит от модуля и связи.
Показания менее сглажены, а после движения платформы могут ещё не установиться.
`Ctrl+C` отменяет измерение и возвращает к командам. Ручная команда `weight fast`
доступна после `main stop`. Сам сортировщик также использует быстрые измерения;
для их просмотра во время сортировки выполните `weight continuous`.
Обычная команда `weight` вне сортировки, тарирование и калибровка сохраняют
выдержку 500 мс и усреднение 10 отсчётов. Аппаратный режим RATE HX711 не меняется.

`main.py` требует `--weight-scale` и передаёт его Arduino после `READY`;
до калибровки `WEIGHT?` возвращает `ERROR HX711_NOT_CALIBRATED`.
Повторное `tare` сохраняет коэффициент. Команда `ZERO` сбрасывает только XY.

Измерение ограничено 4 секундами в прошивке и `weight_timeout=5` в Python.
Ошибка готовности даёт `ERROR HX711_TIMEOUT`, насыщение АЦП —
`ERROR HX711_OVERLOAD`. Читать вес при включённой ленте можно: в контроллере
выполните `conveyor on`, затем `weight continuous`. `Ctrl+C` возвращает к командам,
оставляя ленту включённой; `conveyor off` выключает её.
Во время движения XY чтение веса запрещено. Тарирование и калибровка требуют
остановки и XY, и ленты (`ERROR HX711_MOVING`). Пока выполняется измерение, команды движения
отклоняются (`ERROR HX711_BUSY`); `STOP` отменяет измерение и останавливает XY,
`CONVEYOR OFF` остаётся доступной. Отрицательные показания передаются как есть:
они полезны для диагностики тары и знака коэффициента.

## Главный цикл сортировки

`main.py` содержит автоматический цикл `runWarehouse(hardware, camera, config)`.
Перед первым циклом он останавливает ленту, закрывает затвор и ждёт 0,5 секунды.
Затем один раз явно вызывает `tareWeight()` и ждёт подтверждения `TARED`,
независимо от автоматического тарирования при запуске платы. В этот момент
весовая платформа должна быть пустой. Коэффициент калибровки сохраняется.
При ошибке тарирования сортировка не начинается, оборудование останавливается
и отключается.

1. Подвести головку с уже закрытым затвором к `loading_position` и дождаться
   окончания движения.
2. Сбросить подтверждение предыдущего предмета и проверить камеру на остановленной
   ленте в течение `confirmation_frames` кадров (по умолчанию 3). Если предмет уже
   подтверждён, запуск для поиска пропускается. Иначе включить конвейер, ждать
   подтверждённого предмета и остановить ленту.
3. Использовать основной цвет из подтвердившего предмет кадра. При доле ниже
   60% вывести пометку «смешанные цвета» и продолжить цикл: предмет обнаружен,
   а `ambiguous` сообщает только о распределении цветов внутри него.
   В терминале отображается доля пикселей основного цвета.
4. Сразу после подтверждения предмета и его цвета оставить ленту остановленной
   и измерять вес предмета под камерой в течение `weight_duration` секунд
   (по умолчанию 3 с). `measureWeight()` последовательно вызывает `get_weight(fast=True)`
   и усредняет полученные показания. Каждый запрос усредняет 2 новых отсчёта
   без выдержки в прошивке; нужна прошивка с командой `WEIGHT_FAST?`.
   Последний запрос дочитывается до конца, поэтому
   фактическое время может превышать заданное на время завершения запроса.
   По полученному среднему весу выбрать ряд.
   Внутри ряда `selectCell(weight)` выбирает случайную ячейку; цвет на выбор
   не влияет.
5. Включить конвейер на `feed_duration` секунд, чтобы взвешенный предмет упал
   в тару, затем остановить конвейер. Отвести головку к выбранной ячейке, дождаться окончания движения,
   открыть затвор (0,5 с), дождаться выпадения предмета (0,5 с), закрыть
   затвор (0,5 с).
6. При остановленных ленте и головке вызвать `tareWeight()` и дождаться `TARED`.
   Платформа в этот момент должна быть пустой. После успешного тарирования
   записать сообщение в журнал и повторить с первого шага. Если тарирование
   завершилось ошибкой, следующий объект не обрабатывается, механизмы останавливаются.

| Масса | Ряд | Номера ячеек |
| --- | --- | --- |
| Больше 0 и меньше 5 г | 1 | 1–3 |
| От 5 включительно до 12 г | 2 | 4–6 |
| От 12 г включительно | 3 | 7–9 |

Ровно 5 г относится ко второму ряду, ровно 12 г — к третьему.
Здесь ряды соответствуют группам номеров в `cell_positions`: соответственно
Y=10, Y=5 и Y=0. Учёта заполненности ячеек нет.
При отрицательном показании измерение прекращается, а лента включается и едет
до следующего предмета. Сначала камера должна увидеть пустую область в течение
`confirmation_frames` последовательных кадров, затем подтвердить новый предмет.
Пропущенному предмету ячейка не назначается; головка остаётся у конвейера,
затвор остаётся закрытым. Между предметами нужен видимый камерой промежуток.
Нулевое, неконечное показание и ошибка датчика останавливают цикл
до подачи предмета в тару, движения к ячейке и открытия затвора. Для отсечения положительного шума
можно задать `--min-weight` в граммах; по умолчанию отклоняется вес ≤0.
Порог `--min-weight` проверяется по среднему весу за время измерения.

Этот порядок предполагает, что тензодатчик измеряет вес предмета, пока тот
находится на ленте в области камеры. При размещении весов только под приёмной
тарой взвешивание до подачи физически невозможно.

Лента остановлена во время взвешивания, перемещения головки и выгрузки.
`Camera.isObjectReady()` в этом цикле не используется.
Повторного закрытия перед каждым циклом и искусственных пауз между кадрами нет.
Ожидание `DONE` при движении головки и время подачи `feed_duration` сохраняются.

Настройки находятся в `WarehouseConfig` в `main.py`: `loading_position` —
координаты под конвейером (сейчас `(9.0, 17.0)`), `cell_positions` — координаты
девяти ячеек, `feed_duration` — время подачи после взвешивания (сейчас 0,3 с),
`weight_duration` — время сбора показаний веса на остановленной ленте (сейчас 3 с).
`weight_limits=(5.0, 12.0)` — границы трёх рядов; их можно переопределить
через `--weight-limits 5 12`.
Обе длительности можно переопределить при запуске, например 0,8 с подачи и 4 с взвешивания:

```bash
.venv/bin/python main.py --port COM3 --camera 0 --feed-duration 0.8 --weight-duration 4 --weight-scale=123.45
```

**123.45 здесь только пример** — замените на коэффициент, полученный при калибровке.
На macOS вместо `COM3` укажите порт Arduino вида `/dev/cu.usbserial-…`.
ROI можно заменить флагом `--roi X Y WIDTH HEIGHT`. Порт, координаты и длительность
нужно подобрать под установку. Время подачи должно обеспечивать падение текущего
предмета и не допускать падения следующего: программно таймер не подтверждает
факт падения. При отсутствии предмета поиск продолжается до его появления
или остановки программы. Перед запуском система координат должна быть
откалибрована: `zero()` сбрасывает координаты, но не ищет механический ноль.

Цикл не содержит serial- или GPIO-команд: для другой платы ему передаётся объект
с теми же методами, что у `Hardware`. `createHardware()` — место выбора драйвера.
Для `--backend raspberry-pi` оставлен явный плейсхолдер драйвера, поскольку
распиновка и способ управления Raspberry Pi вместо Arduino пока не определены.
Если Raspberry Pi используется как компьютер с подключённой по USB Arduino,
применяется существующий вариант `arduino` с соответствующим serial-портом.

При ошибке устройства цикл прерывается. Смешанные цвета не останавливают
сортировку, поскольку ряд выбирается по весу и не зависит от цвета.
При выходе, включая `Ctrl+C`, выполняются отдельные попытки остановить головку
(и восстановить синхронизацию протокола через `STOP`), выключить конвейер и отключить оборудование;
ошибка одной операции не отменяет остальные. Камера освобождается в `main()`.

## Проверка

```bash
.venv/bin/python -m unittest discover -s tests -v
```

Тесты проверяют основные цвета на чёрном фоне, тонкий белый предмет на текстурном
коврике с неравномерным освещением и светлыми краями, тёмные насыщенные цвета,
исключение чёрных отверстий, выбор предмета через ROI, разноцветный предмет,
пустой кадр и неверные координаты.
Проверки видеорежима используют последовательности искусственных кадров:
исчезновение предмета и смену цвета, сохранение снимков, отключение камеры и выход.
Фильтры шума проверяются на обоих фонах: мелкие постоянные пятна, короткие вспышки,
плавное движение, скачки положения/размера/цвета, сброс при потере кадра,
переподключении и изменении ROI/разрешения, а также настройка порогов.
Они не заменяют проверку изображения и разрешений на физической веб-камере.
Проверки главного цикла используют имитацию устройств: порядок операций,
поиск на пустой ленте и пропуск поиска при уже видимом предмете, подтверждение
реальным детектором на искусственных кадрах, повторение цикла, ошибки подачи
и движения, настройка времени, прерывание и освобождение оборудования.
Весовые тесты проверяют границы 5/12 г, выбор ячейки нужного ряда, усреднение
за заданное время, остановку ленты до измерения и подачу только после него,
ошибки и прерывание измерения до подачи, тарирование, калибровку, частичные ответы,
таймауты и восстановление serial-протокола. `test_firmware.py` компилирует
настоящий скетч с имитацией GPIO/Serial (нужен C++ компилятор) и проверяет
24-битные знаковые значения, старт, измерения, ошибки и отмену.
Эти тесты не заменяют калибровку и проверку физических весов.
